# AllBrands-Marketplace
# Пітч 
**Проблема**: Покупці витрачають години, перемикаючись між сайтами Nike, Zara Mango і так далі щоб зібрати повний образ. Немає єдиного місця, де можна порівняти ціни та наявність різних брендів одночасно.
**Рішення**: Зробити єдиний маркетплейс-агрегатор, який об'єднує каталоги провідних брендів в одному інтерфейсі з спільним кошиком.
**Цінність**: Економія часу та можливість стилістичного поєднання речей від різних виробників за один візит.
# Ядро цінності (MVP):
Для першої версії ми зосереджуємося на одній ключовій функції:Перегляд об’єднаного каталогу 3-х брендів із можливістю базової фільтрації та додавання товару в кошик.
# Карта стейкхолдерів
**Кінцеві споживачі**: Шопоголіки та люди, що цінують свій час.
**Власник продукту (ви)**: Визначає пріоритети брендів для додавання.
**Менеджери брендів-партнерів**: Надають інформацію про залишки та ціни.
**Розробники**: Забезпечують технічну інтеграцію API різних магазинів.
# Мета та ознаки успіху
**Мета**: Протягом 2-х тижнів розробити прототип, де користувач зможе знайти та додати у кошик речі мінімум 2-х різних брендів.
# Ознаки успіху:
Система стабільно відображає товари різних брендів в одній сітці.Функція «Додати в кошик» працює без помилок для кожного бренду. 
# Сценарій користувача 
**Початок**: Користувач заходить на головну сторінку з метою знайти білі кросівки та чорні джинси.
1. Використовує фільтр «Бренд» і обирає «Nike» та «Levi's».
2. Обирає модель кросівок, вказує розмір і натискає «В кошик».
3. Повертається до списку, обирає джинси та також додає їх у кошик.
4. Переходить у кошик і бачить обидва товари від різних брендів з правильною сумою.
**Результат**: Сформовано замовлення, що містить товари різних виробників.
**Приклад**: docs/user-scenario.md
# Критерії приймання 
**Пошук**: Рядок пошуку має видавати результати за назвою бренду або категорією одягу.
**Продуктивність**: Перехід між сторінками брендів має тривати не більше 1.5 сек.
**Юзабіліті**: Кнопка «Купити» має бути помітною (контрастною) та доступною з мобільних пристроїв.
# План перевірки гіпотез
**Гіпотеза 1**: Користувачам важливіше мати вибір брендів, ніж глибокий опис кожної речі.
**Метод**: Тестування на фокус-групі з 5 людей. Спостереження: чи намагаються вони читати детальний склад тканини, чи відразу переходять до вибору іншого бренду.
**Гіпотеза 2**: Користувачі будуть частіше купувати "комплектом" (кросівки + штани), якщо бачитимуть їх на одній сторінці.
**Метрика**: Відсоток замовлень, що містять >1 бренду. 
# Управління ризиками та невизначеністю
**Ризик**: Різні розмірні сітки у брендів (наприклад, L у Zara може бути як M у H&M).
**Мінімізація в MVP**: Додати коротку підказку "Таблиця розмірів бренду" біля кожного товару замість складної системи автоматичного підбору.
**Технічний ризик**: Відключення API стороннього бренду.
**Мінімізація**: Кешування даних про товари на 1 годину. 
# Definition of Success (DoS) для першої ітерації
Користувач успішно завершує сценарій купівлі (від пошуку до натискання "Оформити") без сторонньої допомоги.
**Час виконання сценарію**: не більше 2 хвилин.
# Стабільність: 0 критичних помилок (crash) при одночасному додаванні товарів від 5 різних брендів.
